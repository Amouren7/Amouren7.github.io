> 本文是个人项目《电商 RAG 客服 Agent》的完整复盘。从「为什么做」到「踩了哪些坑」，一次讲清楚。

## 为什么做这个项目

面试里人人都在聊 RAG，但真正落地过的人不多。我想做一个**能回答"基于我的知识库"的问题**的客服 Agent，证明自己不是只会背概念。

技术选型：**DeepSeek/Qwen 大模型 API + 向量检索 + FastAPI**。为什么选这些？一是国内可直连，二是成本低，适合个人项目反复实验。

## 核心链路

```
用户提问
  → 检索（embedding 相似度召回 top-k）
  → 重排（关键词 + 语义混合，简单的 score 融合）
  → 组装 prompt（知识片段 + 历史会话 + 指令）
  → LLM 生成回答（流式输出）
  → 引用标注（回答里标注知识来源 id）
```

最容易被忽略的是**引用标注**——没有来源的 RAG 回答不可信，客服场景尤其致命。我让模型在回答末尾输出 `[[来源: doc-xxx]]`，前端渲染成可点击的脚注。

## 踩过的坑

### 1. 分块策略：一刀切 chunksize 是错的
一开始用固定 500 token 切块，长文档被腰斩，检索质量很烂。后来改成**标题感知分块**（按 markdown 标题层级切，保留上下文）＋对表格单独处理，召回准确率明显提升。

### 2. 检索不到 ≠ 模型不行，而是"问法对不上"
用户口语「你们发不发新疆」vs 知识库「新疆/西藏不包邮」。做了一组**问题改写（query rewrite）**：先用小模型把口语归一化成检索式，再进向量库。召回率涨了大概 15%。

### 3. 流式 + 中文乱码
FastAPI 的 StreamingResponse 如果没设置正确的 `media_type` 和编码，中文会断字。用 `text/event-stream; charset=utf-8`，前端用 fetch 逐段解析 SSE。

### 4. 评测不能靠感觉
我搞了一个 20 题的黄金评测集，覆盖「精确引用 / 拒答 / 越权回答」三类，每次改完跑一遍记分。**没有评测的 RAG 就是玄学调参。**

## 数据说话

- 黄金集 20 题，综合通过率从初版 55% 提到 82%
- 端到端首 token 延迟 < 1.2s（DeepSeek 流式）
- 单并发下成本约 ¥0.003/次对话

## 一句话总结

RAG 的价值不在模型，在于**检索质量 + 评测闭环**。把这两件事做扎实，效果自然就上来了。
